NotificationView DTO (all columns, camelCase)

BuildAC-017
A local, immutable view type exposing every column of the notification table. Record-style accessors and a Lombok builder are pinned by the tests and the fixture.
  • web/NotificationView — a Java record annotated @Builder; components notificationId(UUID), notificationType, status, sendToAddress, statusCode(Integer), errorMessage, clientContext, resultQueue, createdAt/updatedAt(OffsetDateTime)
  • Lombok emits NotificationView.builder() -> NotificationViewBuilder — the exact type NotificationViewFactory.aNotificationView() returns
  • Record accessors view.notificationId() … view.updatedAt() satisfy NotificationQueryServiceTest; component names serialise as camelCase JSON keys (Jackson default)
Contract shape. Required vs nullable mirrors the spec's NotificationView schema: required notificationId/notificationType/status/createdAt/updatedAt; nullable sendToAddress/statusCode/errorMessage/clientContext/resultQueue. Plain record (no @JsonInclude) — nulls serialise as JSON null, which the nullable:true schema accepts, and the test data is all-non-null so the fixture matches. Jackson 3: OffsetDateTime → ISO-8601 (2026-07-01T09:00:00Z). Option B: DTO is local, not generated; contract-first migration tracked as debt in query-api-implementation.md.

NotificationRepository.search (nullable filters, paged)

BuildAC-018
Add a paged search to the existing Spring Data repository — status + created-range filters, all nullable, returning a page of entities.
  • persistence/NotificationRepository — add Page<NotificationEntity> search(String status, OffsetDateTime from, OffsetDateTime to, Pageable pageable)
  • @Query with null-guarded predicates: (:status is null or status = :status) and (:from is null or createdAt >= :from) and (:to is null or createdAt <= :to)
  • Proven by NotificationRepositoryIntegrationTest.Search over Testcontainers Postgres — only the in-range FAILED row is returned
Parameterised query, no string concatenation (OWASP injection, NFR-006). Bind params only; nullable filters handled in-clause so a single method serves id-less, status-less and range-less callers.

4

NotificationQueryController + validation advice

BuildAC-017/018 · conformance · 400s · NFR-004
Hand-written @GetMappings (Option B) on /notifications: single lookup + paged search, with Jakarta param constraints mirroring the spec. No write mappings → 405 automatically.
  • web/NotificationQueryController — @RestController @Validated @RequestMapping("/notifications"), constructor-injected NotificationQueryService
  • @GetMapping("/{notificationId}") → findById; present → ResponseEntity.ok(view), empty → notFound().build() (404, empty body so the spec's content-less 404 conforms)
  • @GetMapping search — @RequestParam(required=false) @Pattern(regexp="QUEUED|SENT|FAILED") String status; createdFrom/createdTo as @DateTimeFormat(iso=DATE_TIME) OffsetDateTime; @RequestParam(defaultValue="0") @Min(0) int page; @RequestParam(defaultValue="20") @Min(1) @Max(200) int size → PageRequest.of(page,size), returns Page<NotificationView> (content array conforms to NotificationPage)
  • No POST/PUT/PATCH/DELETE mappings → 405 before the controller runs (verifyNoInteractions holds)
  • web/QueryApiExceptionHandler — @RestControllerAdvice mapping ConstraintViolationException (and MethodArgumentTypeMismatchException) → 400, status-code-only body
The 400 crux. Type-mismatch (bad createdFrom/UUID) is 400 automatically, but @Min/@Max/@Pattern on request params throw a bare ConstraintViolationException → 500 unless handled — the four SearchParameterValidation tests fail without the advice. @Validated on the class arms method-param validation; the advice maps the violation to 400. NFR-004: the handler logs no PII/params/values and returns no stack trace or entity dump.

SecurityConfig — interim permit-all + deps

Buildinterim · until NG-S14
Add spring-boot-starter-security and an interim permit-all filter chain, active in every profile and clearly commented as open until NG-S14 delivers authentication. No profile split, no deny — the deny posture was descoped to NG-S14.
  • build.gradle — add implementation 'org.springframework.boot:spring-boot-starter-security' (spring-boot-starter-validation already present; swagger-request-validator-mockmvc already a test dep)
  • web/SecurityConfig — @Configuration @EnableWebSecurity; single SecurityFilterChain = anyRequest().permitAll(), CSRF disabled, stateless; actuator permitted too; comment marks it open until NG-S14
Why permit-all, all profiles. The secure-by-default deny posture and its auth pattern moved to NG-S14; the deny integration test was removed. Adding the starter with an explicit permit-all chain makes Boot's default (secure) chain back off, so the full-context sanity/BDD suite and /actuator/* behave exactly as their tests expect — served open. The controller/conformance slices use addFilters=false and are unaffected either way.
